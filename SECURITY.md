# Security Policy

SteamTrophies runs inside or alongside software users trust with their Steam session, local files and gaming environment. Security issues therefore receive the same seriousness as crashes or trophy-data loss.

## Supported versions

Until the first stable public release, security fixes are applied to the current release-candidate branch. After stable releases begin, this file should be updated with the maintained version window.

## Reporting a vulnerability

Please report suspected vulnerabilities privately to the repository owner/maintainers using GitHub's private vulnerability reporting feature if it is enabled for the repository.

If private vulnerability reporting is not enabled, contact the maintainer through a private channel listed on the repository before publishing reproduction details.

Please include, when possible:

- affected version or commit
- operating system and Steam channel
- Millennium/Decky version
- threat scenario
- exact reproduction steps
- proof-of-concept files if relevant
- whether user interaction is required
- whether data disclosure, arbitrary code execution, host instability or persistence is possible

Do not include real Steam Web API keys, session secrets or unrelated personal data.

## Security boundaries

### User resource packs

User-installed trophy packs are data-only. They must not be treated as trusted code.

The importer is expected to reject:

- absolute paths and traversal
- symlinks and link-like entries
- undeclared payloads
- unsupported file formats
- executable/script masquerading
- excessive file counts or byte sizes
- excessive decoded image dimensions/pixel counts
- reserved built-in namespaces
- malformed or unsupported manifests

Supported user image/audio formats remain intentionally narrow.

### Filesystem RPC

Renderer-callable backend methods must expose capabilities, not arbitrary paths. Game shard operations use numeric App IDs and known storage roots. Do not add generic read/write/delete RPC methods merely for convenience.

### Network access

The plugin should remain local-first. Network access must be allowlisted and purpose-specific.

Steam Web API keys, if a keyed fallback is enabled, must never be placed in:

- renderer state
- query strings
- logs
- screenshots
- backups
- resource packs
- crash reports

### Steam private UI integration

Steam private UI changes frequently. Hook transforms must be minimal, target the exact current build, validate their anchor and fail closed when the expected structure is absent.

A missing trophy entry is preferable to patching unknown Steam JavaScript.

### Persistence

Persisted state is treated as untrusted input on read. Structural validation occurs before state replacement. Critical files should use atomic replacement, constrained backups and corruption quarantine.

### Dependency and build integrity

The release repository should commit a real npm lockfile generated by npm, use pinned direct dependency versions, run dependency audits in the networked finalization environment and produce release artifacts from a clean tested commit.

## Security validation

Offline security gates include:

```bash
npm run security:audit
npm run security:pack-corpus
npm run release:validate
```

The static audit intentionally rejects dangerous runtime patterns such as arbitrary evaluation, child processes, raw HTML injection, raw `file://` construction and unexpected network hosts.

The hostile-pack corpus tests traversal, reserved namespaces, executable masquerading, size limits, decoder-bomb dimensions, undeclared files and malformed manifests.

## Out of scope for public issue proof-of-concepts

Please avoid publicly posting weaponized material involving:

- Steam session theft
- arbitrary code execution
- filesystem escape
- credential/API-key disclosure
- reliable Steam client crash loops

A minimal private reproduction is enough for maintainers to investigate.
